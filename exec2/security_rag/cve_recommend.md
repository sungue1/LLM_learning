|---|---|---|---|---|---|
| 1 | `CVE-2021-44228` | **Log4Shell** | CWE-20, 400, **502**, 917 | 10.0 | 역직렬화 |
| 2 | `CVE-2014-6271` | **Shellshock** | CWE-78 | 9.8 | OS 명령 주입 |
| 3 | `CVE-2016-2386` | SAP SQL 인젝션 | CWE-89 | 9.8 | SQL 주입 |

### 수집 명령

```bash
cd security_rag
python src/0_fetch_real_data.py \
  --cve-ids CVE-2021-44228 CVE-2014-6271 CVE-2016-2386 CVE-2014-0160 CVE-2019-0708 \
  --max-cves 0
python src/1_chunk.py
python src/2_embed_and_store.py
```

> **`--max-cves 0`이 반드시 필요합니다.** 빼면 KEV 200건이 추가로 붙습니다.
> `--cve-ids`는 "반드시 포함"이지 "이것만"이 아닙니다.

## 먼저 알아야 할 제약 — 못 쓰는 유명 CVE가 있습니다

이 파이프라인은 **CWE를 열쇠로 삼습니다.** NVD가 CWE를 분류하지 않은 CVE는
`--cve-ids`로 콕 집어 지정해도 **수집 단계에서 제외됩니다.**

실제로 확인한 결과입니다.

```
[NVD] CVE-2021-44228 -> CWE-20, CWE-400, CWE-502, CWE-917
[NVD] CVE-2014-0160  -> CWE-125
[NVD] CVE-2014-6271  -> CWE-78
[NVD] CVE-2019-0708  -> CWE-416
[NVD] CVE-2016-2386  -> CWE-89
[NVD] CVE-2017-0144: CWE 매핑이 없어 건너뜀     ← EternalBlue
[NVD] CVE-2018-11776: CWE 매핑이 없어 건너뜀    ← Struts2
[NVD] CVE-2021-34527: CWE 매핑이 없어 건너뜀    ← PrintNightmare
```

| 못 쓰는 CVE | 별칭 | 이유 |
|---|---|---|
| `CVE-2017-0144` | **EternalBlue** (WannaCry) | NVD가 `NVD-CWE-noinfo`로 남겨둠 |
| `CVE-2018-11776` | Struts2 RCE | 위와 같음 |
| `CVE-2021-34527` | PrintNightmare | 위와 같음 |

가장 유명한 축인데 쓸 수 없습니다.

> **이 사실 자체가 좋은 교육 소재입니다.**
> "유명한 사건이라고 데이터가 있는 것은 아니다"를 보여줍니다.
> 수업에서 일부러 `CVE-2017-0144`를 물어보게 하면,
> RAG가 "데이터에 없다"고 답하는 이유를 몸으로 이해하게 됩니다.

## 선정 기준 ① — 취약점 계열이 겹치지 않을 것

5건이 서로 다른 계열을 담당합니다.

```
[주입 계열] 입력이 코드·명령·쿼리로 해석되는 문제
  CWE-502  역직렬화        신뢰할 수 없는 데이터를 객체로 되살림
  CWE-78   OS 명령 주입     입력이 셸 명령이 됨
  CWE-89   SQL 주입         입력이 SQL 구문이 됨

[메모리 계열] 메모리 경계·수명을 잘못 다루는 문제
  CWE-125  경계 밖 읽기     읽으면 안 되는 메모리를 읽음 (정보 유출)
  CWE-416  Use After Free   해제된 메모리를 다시 사용 (코드 실행)
```

**예방 방법이 계열마다 완전히 다릅니다.**

| 계열 | 예방 방향 |
|---|---|
| 주입 | 입력 검증, 파라미터화 쿼리, allowlist, 이스케이핑 |
| 메모리 | 메모리 관리 언어 사용, 컴파일러 보호 옵션(`/GS`, `FORTIFY_SOURCE`), ASLR |

같은 질문("어떻게 예방하나요?")을 던져도 **답의 성격이 갈리는 것**을 보여줄 수 있습니다.
계열이 겹치면 이 대비가 사라집니다.

## 선정 기준 ② — CWE 문서가 충실할 것

RAG 실습은 **검색해 올 근거가 있어야** 성립합니다.
MITRE 카탈로그에서 섹션별 글자 수를 실측했습니다.

| CWE | 설명 | 상세 | **완화 방법** | **사례** | 판정 |
|---|---|---|---|---|---|
| CWE-78 | 269 | 2,294 | **10,130** | 2,467 | 최상 |
| CWE-89 | 455 | 0 | **7,840** | 1,355 | 최상 |
| CWE-787 | 86 | 0 | 3,526 | 2,375 | 좋음 |
| CWE-125 | 85 | 0 | 1,522 | 1,631 | 좋음 |
| CWE-502 | 108 | 0 | 2,022 | 1,472 | 좋음 |
| CWE-416 | 376 | 0 | 282 | **2,894** | 사례 중심 |
| CWE-20 | 179 | 1,772 | 5,408 | 4,305 | 최상 |
| CWE-400 | 91 | 0 | 1,671 | 2,224 | 좋음 |
| CWE-917 | 323 | 342 | 586 | 136 | 보통 |
| **CWE-755** | 76 | 0 | **0** | 834 | **부적합** |

`potential_mitigations`가 길어야 **"어떻게 예방하나요?"** 질문에서
청크 분할과 검색이 제대로 시연됩니다.

CWE-78(10,130자)과 CWE-89(7,840자)는 1,200자 제한 때문에 **여러 조각으로 나뉩니다.**
[2_chunk.ipynb](2_chunk.ipynb)의 `split_long_section()` 실습과 그대로 맞물립니다.

## 선정 기준 ③ — 서로 다른 것을 가르칠 것

각 CVE가 담당하는 교육 포인트가 다릅니다.

### 1. Log4Shell — 복수 CWE 매핑

**CWE가 4개 붙은 유일한 사례**입니다.

```python
mapping["CVE-2021-44228"]["cwe_ids"]
# → ['CWE-20', 'CWE-400', 'CWE-502', 'CWE-917']

where={"cwe_id": {"$in": ["CWE-20", "CWE-400", "CWE-502", "CWE-917"]}}
```

`$in` 필터가 **여러 CWE를 한 번에 감싸는** 동작을 보여줍니다.
나머지 4건은 CWE가 하나씩이라 필터가 단순합니다.
**하나 정도는 복수 매핑이 있어야** 메타데이터 필터의 진짜 모양이 드러납니다.

CVSS 10.0에 가장 유명한 사건이라 **수업 도입부로도 적합**합니다.

### 2. Shellshock — 가장 풍부한 완화 문서

CWE-78의 완화 방법이 **10,130자**로 후보 중 최대입니다.
청크가 여러 개로 쪼개지므로 "질문에 따라 다른 조각이 걸리는" 모습을 관찰하기 좋습니다.

### 3. SAP SQL 인젝션 — 가장 익숙한 취약점

CWE-89(SQL 인젝션)는 **교육생이 이미 아는 개념**입니다.
RAG가 찾아온 답이 맞는지 **스스로 검증할 수 있는** 유일한 사례입니다.
다른 CVE는 답이 맞는지 판단하기 어렵습니다.

### 4. Heartbleed — 읽기 계열 대표

메모리를 **읽기만 해도** 심각한 유출이 된다는 점을 보여줍니다.
CVSS 7.5로 5건 중 가장 낮은데, **점수와 실제 파급력이 비례하지 않는다**는
이야기를 꺼내기에도 좋습니다.

### 5. BlueKeep — 섹션별 검색 시연용 ⭐

**일부러 넣은 사례입니다.** CWE-416은 완화 방법이 282자로 짧고
**사례가 2,894자로 압도적**입니다.

같은 CVE에 질문만 바꿔 던지면 **다른 섹션이 걸립니다.**

```
"어떻게 예방하나요?"      → potential_mitigations
"실제 사고 사례가 있나요?"  → observed_examples
"이게 뭔가요?"            → description
```

**섹션 단위 청킹의 효과를 눈으로 확인시키는 데 가장 좋은 사례**입니다.
[4_query.ipynb](4_query.ipynb)의 검색 실습에서 이 CVE를 쓰면 효과가 큽니다.

## 수업 진행 예시

```bash
# 도입 — 가장 유명한 사건
python src/3_query.py CVE-2021-44228 "why is this dangerous?"

# 계열 대비 — 주입 vs 메모리
python src/3_query.py CVE-2014-6271 "how should developers prevent this?"
python src/3_query.py CVE-2014-0160 "how should developers prevent this?"

# 검증 가능한 사례 — 학생이 답을 판단할 수 있음
python src/3_query.py CVE-2016-2386 "how to prevent SQL injection?"

# 섹션별 검색 시연 — 같은 CVE, 다른 질문
python src/3_query.py CVE-2019-0708 "how should developers prevent this?"
python src/3_query.py CVE-2019-0708 "what real-world incidents came from this?"

# 실패 사례 — 데이터에 없는 CVE
python src/3_query.py CVE-2017-0144
```

마지막 명령은 **일부러 실패하게** 하는 것입니다.
안내 문구가 왜 그렇게 답하는지 설명하면, 이 프로젝트의 설계와 한계가 한 번에 전달됩니다.

## 참고 — 200건을 유지할지, 5건으로 교체할지

| 방식 | 명령 | 장점 | 단점 |
|---|---|---|---|
| **5건만** | `--max-cves 0` 추가 | 데이터가 작아 청크·색인이 빠름, 시연이 깔끔 | "없는 CVE" 상황을 만들기 쉬움(의도적이라면 장점) |
| **200건 + 5건** | `--max-cves 0` 생략 | 역방향 조회·통계 실습 가능 | 색인 시간과 비용 증가 |

수업에서 **"데이터에 없는 CVE"** 상황을 보여주실 계획이라면 5건만으로도 충분합니다.
[1_fetch.ipynb](1_fetch.ipynb)에서 수집 조건을 바꿔가며 비교해 보는 것도 좋은 실습입니다.
